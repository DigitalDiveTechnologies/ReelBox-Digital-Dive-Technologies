2. Purpose
This document defines the functional, technical, data, security, integration, and user-experience 
requirements for a mobile application that receives Instagram or Facebook reel/video links through the 
operating-system share sheet or manual URL entry, processes the link through a backend downloader 
pipeline, stores the downloaded media in managed object storage, records metadata in PostgreSQL, and 
presents the saved media inside the application library.
3. Product Scope
The MVP will allow a user to share a supported public or otherwise legitimately accessible 
Instagram/Facebook media link to the application. The application will automatically detect the platform, 
submit the link, show download status, and display the media in a persistent library once processing 
succeeds. Manual URL paste is retained as a fallback. The system is designed so additional providers can 
be added later without changing the mobile contract.
4. Goals and Non-Goals
4.1 Goals
 Make saving a reel/video a low-friction action: Share -> select the app -> automatic processing.
 Keep long-running download work outside the mobile UI and outside synchronous API requests.
 Persist media metadata, source platform, source URL, timestamps, status, and storage location.
 Provide a clean media library with playback, filtering, retry, and deletion capabilities.
 Keep the download provider replaceable through a provider/extractor abstraction.
 Support future platforms such as TikTok, X, YouTube, or Pinterest without redesigning the core 
pipeline.
4.2 Non-Goals for MVP
 Social-network account publishing, commenting, liking, or analytics.
 Downloading content that the user is not authorized or permitted to access.
 Editing or transcoding videos beyond optional thumbnail generation and basic validation.
 Storing large video binaries directly inside PostgreSQL.

8. Functional Requirements
FR-001 - Receive Shared URL
The mobile application shall accept URLs shared from supported applications through the operating-
system share mechanism.
Acceptance: Sharing a supported Instagram/Facebook URL opens or invokes the application and 
supplies the URL without requiring manual paste.
FR-002 - Manual URL Entry
The mobile application shall provide a URL input as a fallback.
Acceptance: A valid supported URL entered manually can be submitted with the Save action.
FR-003 - Platform Detection
The system shall determine the source platform from the submitted URL.
Acceptance: Instagram and Facebook URLs are classified correctly; unsupported domains are rejected 
with a useful message.
FR-004 - URL Validation
The backend shall validate syntax, scheme, supported host/domain, and request constraints before 
queueing.
Acceptance: Malformed or unsupported URLs never create a download job.
FR-005 - Create Media Record
The backend shall create a persistent media record before asynchronous processing starts.
Acceptance: Every accepted request has a unique media ID and initial status.
FR-006 - Queue Download Job
The backend shall enqueue download work instead of downloading within the request thread.

FR-009 - Upload Media
The worker shall upload completed media to object storage and record the storage key.
Acceptance: Completed records reference an existing object-storage key.
FR-010 - Generate Thumbnail
The system should generate or retain a thumbnail when feasible.
Acceptance: Completed items display a thumbnail; absence of thumbnail does not block successful 
save.
FR-011 - Persist Metadata
The system shall store platform, original URL, status, created time, download times, storage key, file 
size, and failure information.
Acceptance: Metadata remains available after app restart/login.
FR-012 - Progress / Status
The mobile app shall receive or retrieve the latest processing status.
Acceptance: A user can see whether a media item is queued, downloading, completed, or failed.
FR-013 - Library Listing
The backend shall provide paginated media-library results for the authenticated user.
Acceptance: Library loads saved items ordered by most recent by default.
FR-014 - Media Playback
The user shall be able to play successfully saved media from the application.
Acceptance: Tapping a completed item opens a playable media view using an authorized delivery 
URL.
FR-015 - Retry Failed Download
Eligible failed jobs shall be retryable.
Acceptance: Retry creates/requeues work without creating duplicate completed media accidentally.
FR-016 - Delete Media
The user shall be able to delete a saved item.
Acceptance: Deletion removes or schedules removal of the object and removes/hides the library 
record according to retention policy.
FR-017 - Duplicate Handling
The system should detect repeated save requests for the same user/source URL.

11. Downloader Service Design
The downloader service is a backend worker and is not exposed directly to the mobile UI. It consumes 
queued jobs and implements platform-specific behavior through replaceable providers.
IDownloadProvider / IMediaExtractor
          |
          +-- InstagramProvider
          +-- FacebookProvider
          +-- OptionalThirdPartyProvider
          +-- FutureProvider
Worker Step Description
1. Consume Read a media job from the queue.
2. Load record Load media item and verify it is eligible to process.
3. Select provider Choose provider using normalized platform classification.
4. Resolve Resolve media metadata/source subject to access and policy 
rules.
5. Download Stream media using configured timeout, size, and network 
limits.
6. Validate Verify content type/format and basic file integrity.
7. Thumbnail Generate or save thumbnail when available.
8. Upload Upload final object(s) to object storage.
9. Complete Update PostgreSQL status, timestamps, size, keys, and error 
fields.

12.2 Recommended Indexes
 Index on (user_id, created_at DESC) for library queries.
 Index on (user_id, status) for pending/failed filters.
 Optional unique/partial policy on (user_id, normalized_url) when duplicate prevention is enabled.
 Index on status / next_retry_at if workers query the database in addition to the queue.
13. Media State Machine
PREPARING -> QUEUED -> DOWNLOADING -> PROCESSING -> COMPLETED
                 \______________________________> FAILED
FAILED --retry--> QUEUED
Only valid state transitions should be permitted. COMPLETED is terminal unless the user deletes the item; 
FAILED may be retried based on error type and retry policy.

16. Security, Privacy, and Platform Compliance
 The backend shall validate URLs and defend against SSRF by restricting outbound 
resolution/download targets to approved platform/provider flows and safe resolved hosts.
 The system shall not attempt to bypass authentication, paywalls, DRM, private-account controls, or 
other access restrictions.
 Users should save only content they are authorized to access and store; product terms and UX should 
communicate this responsibility.
 Credentials, provider tokens, cookies, and API keys must remain server-side and must not be 
embedded in the mobile application.
 Playback URLs should be access-controlled or time-limited when private object storage is used.
 Delete operations should remove managed media according to the product retention policy.
 Rate limiting and abuse controls should be applied per user/IP/device where appropriate.
 Platform-specific implementation must be reviewed against applicable Instagram/Facebook/Meta 
terms and legal requirements before production launch.

19. End-to-End Sequence
1. User taps Share in Instagram/Facebook.
2. User selects the application from the share sheet.
3. App receives the shared URL.
4. App calls POST /api/v1/media.
5. API validates URL, creates DB record, enqueues job.
6. API returns media ID + QUEUED status.
7. Worker consumes job and sets DOWNLOADING.
8. Provider resolves permitted media source.
9. Worker downloads and validates media.
10. Worker uploads video/thumbnail to object storage.
11. Worker updates DB to COMPLETED with storage metadata.
12. App receives/polls status and updates UI.
13. Item appears in Library and can be played.
20. MVP Acceptance Criteria
 AC-01: A user can share a supported Instagram URL to the app and the URL is received automatically.
 AC-02: A user can share a supported Facebook URL to the app and the URL is received automatically.
 AC-03: A user can paste a supported URL manually when share integration is unavailable.
 AC-04: Accepted requests create a persistent media item and asynchronous job.
 AC-05: The API does not wait for full media download before responding.
 AC-06: The app displays queued/downloading/completed/failed state.

Appendix B - Definition of Done for a Download
 The item belongs to the authenticated user.
 The source URL and platform are persisted.
 The final media object exists in managed object storage.
 The database contains the correct media storage key and file metadata.
 Status is COMPLETED and downloaded_at is populated.
 The mobile app can request an authorized playback URL and play the media.
 No sensitive provider credentials are exposed to the client.
